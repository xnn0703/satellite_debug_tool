# M31 出货固件、参数基线与最终 IP 自动整备计划

## 1. 目标

在正式自动工况开始前，为每台参与设备执行可追溯的出货状态整备：

1. 校验设备身份和产品型号。
2. 比较当前固件与已认证解密的出货固件；不一致时执行 OTA，并用重启后的同一设备身份和版本回读确认应用结果。
3. 比较当前参数表与版本化出货参数基线；只写入不一致的受管参数，并逐项读回确认。
4. 测试期间保持每台设备唯一的临时 IP。
5. 全部网络相关测试和证据收尾完成后，逐台写入最终出货网络配置并隔离验证。

任何整备步骤未得到设备回读确认时，该设备不进入后续正式工况。

## 2. 已确认的现有能力与缺口

### 已有能力

- 客户 OTA 使用不可变的 AES-256-GCM 固件包，认证解密后校验产品、硬件类型、版本策略、固件大小和 SHA-256。
- `OtaController` 独占设备事务，执行分片传输、ACK 匹配、重启等待、同一身份返回和目标版本确认。
- `ParameterController` 可以读取完整参数表，逐项写入，并以新的参数表读回值确认写入结果。
- 设备会话已经保存硬件 UID、SN、MAC、endpoint 和连接代际，能够识别 endpoint 迁移与身份冲突。
- 批次产品模板已经支持期望固件文本，但尚未引用不可变固件资产或参数基线。

### 当前缺口

- 试产流程尚未拥有 OTA 和参数控制器的设备级整备状态机。
- 没有版本化、带类型和 SHA-256 的参数基线包。
- 参数字段尚未按“受管出货值、设备身份值、网络生命周期值、设备独有校准值”分类。
- 当前协议文档没有证明所有产品都存在可写 IP 参数及写入后的重连合同。
- 多台设备最终使用相同出货 IP 时，不能在同一广播域同时完成在线确认。

## 3. 出货配置包

产品模板引用一个不可变 `ProvisioningBundle`：

```text
provisioning_bundle/
├── manifest.json
├── firmware.sfpkg
├── parameters.json
└── network.json
```

`manifest.json` 保存：

- 配置包 ID、revision、产品型号和允许的硬件类型。
- 固件包 SHA-256、目标版本、AES 算法和加密 key ID。
- 参数基线 SHA-256、schema 版本和适用固件范围。
- 网络配置 SHA-256。
- 创建人、创建时间、说明和软件最低版本。

导入时先验证全部文件、引用、AES-GCM 认证、SHA-256 和产品范围，再原子写入生产配置目录。批次创建后只引用冻结的 bundle ID、revision 和各文件 SHA-256。

## 4. 参数基线模型

### 4.1 显式字段所有权

每个参数必须属于一个明确类别：

- `managed`：出货基线统一管理，参与比较和自动写入。
- `identity`：SN、MAC、硬件 UID 等设备身份，只读且不参与基线写入。
- `network_runtime`：测试期间的临时 IP、掩码、网关和端口，由网络生命周期状态机管理。
- `network_shipping`：最终出货网络配置，只在最终阶段写入。
- `device_specific`：设备独有校准、标定或制造数据，必须有独立来源，不能被通用基线覆盖。
- `observed`：状态和统计项，只读。

不使用“比较时临时忽略 SN/MAC/IP”这种字段黑名单。只有 schema 明确声明为 `managed` 的参数才能自动写入。

### 4.2 类型化比较

`parameters.json` 每项包含名称、协议类型、目标值、比较规则、写入顺序、是否要求重启和适用条件：

- 整数、枚举、布尔和字符串做规范化后的精确比较。
- 浮点参数使用该参数明确给出的绝对容差，不使用全局模糊容差。
- IP、掩码和网关使用结构化解析后比较；MAC 只参与身份核对。
- 未知参数、类型变化、重复参数、缺少必需参数或设备回报只读时明确失败。

参数基线优先由软件从一台已确认黄金样机读取后选择字段并导出，再由审核者确认；不直接把任意 Excel 文本当作可写命令。后续如需 Excel 导入，先映射到同一严格 JSON schema 并预览差异。

## 5. 单设备整备状态机

每台设备由一个 `DeviceProvisioningCoordinator` 负责，复用该设备 Runtime 的事务网关：

1. `identity_ready`：确认产品、协议、硬件 UID、SN、MAC 和当前 endpoint 完整且无冲突。
2. `firmware_compared`：冻结当前多来源固件事实，与加密包目标版本比较。
3. `firmware_updating`：仅在版本不一致时启动 OTA。
4. `firmware_confirmed`：同一不可变设备身份重新上线，所有固件来源一致并匹配目标版本。
5. `parameters_read`：读取本连接代际的完整参数表。
6. `parameters_applying`：按依赖顺序只写差异项，每项等待 ACK 和读回。
7. `parameters_confirmed`：重新读取整表并确认全部 `managed` 参数。
8. `ready_for_test`：冻结整备快照，允许进入正式工况。

固件已经匹配时不重复 OTA；参数已经匹配时不重复写入。固件更新总是在参数整备之前，避免固件升级重置或迁移参数后得到错误结论。

任一状态失败时设备进入 `provisioning_failed`，保存已确认事实和失败原因，批次对该设备标记 `INCOMPLETE`。流程不以超时推断设备已应用固件或参数。

## 6. 多设备临时 IP

### 6.1 测试期间

- 测试 endpoint 与设备身份分离；硬件 UID 是 endpoint 迁移前后的首选关联键。
- 每个槽位保存唯一临时 IP，例如 `192.168.1.101`～`192.168.1.104`。
- 若设备初始 IP 已唯一且可达，可以直接使用，不做无意义写入。
- 若需要改临时 IP，必须逐台供电或使用独立交换机端口隔离，向当前 endpoint 写入，等待旧 endpoint 消失、新 endpoint 出现，并确认硬件 UID、SN 和 MAC 仍属于同一设备。
- 未确认身份迁移时不得把新 endpoint 绑定到原设备 attempt。

自动改 IP 只有在目标产品的参数表明确暴露可写网络字段，并完成“写入、重启/应用、重连、身份一致”真机合同后才启用；否则界面给出人工配置门禁。

### 6.2 最终出货 IP

最终出货 IP 在以下步骤全部结束后执行：

1. 所有依赖网络的自动工况完成。
2. 每台设备的原始 SDB、夹具证据和测试结果已冻结。
3. 报告快照已经保存当前测试 endpoint 与目标出货网络配置。
4. 电源和交换机具备逐槽隔离条件。

若多台设备最终使用相同 IP，按槽位逐台执行：

1. 只给一个槽位供电或只连接一个交换机端口。
2. 写入最终 IP、掩码、网关和端口。
3. 等待设备按协议应用或重启。
4. 在隔离网络中以最终 IP 重连，核对同一硬件 UID、SN、MAC 和网络读回。
5. 保存确认记录后断开该设备，再处理下一台。

因此不能在全部设备仍同时连接时，把它们一起改成相同的出货 IP。

## 7. 流程接入

正式批次顺序调整为：

1. 创建批次并冻结产品模板、ProvisioningBundle 和工作站档案。
2. 发现设备并冻结参与身份。
3. 对每台设备执行固件和参数整备。
4. 全部设备进入 `ready_for_test` 后，启动静态、摇摆和上电工况。
5. 受控停止、关闭电源并冻结证据。
6. 逐台应用并验证最终出货网络配置。
7. 生成报告与 manifest；报告同时记录测试 endpoint 和最终出货配置确认。

生产页面增加“出货整备”区域，显示每台设备的固件当前/目标版本、参数差异数、写入进度、临时 IP、目标出货 IP和最终确认状态。开始测试按钮只依据 coordinator 的 `ready_for_test` 事实启用。

## 8. 证据与报告

每台设备保存：

- ProvisioningBundle manifest、固件包 SHA-256、参数基线 SHA-256。
- 整备前后的固件多来源事实。
- 参数整备前快照、差异、每项写入 ACK、读回和最终完整快照。
- 测试临时 endpoint 的来源和所有迁移记录。
- 最终出货网络写入、重连身份和读回证据。
- 操作者、软件版本、时间、结果和失败原因。

报告将“出货配置一致性”作为测试前置与最终配置两个独立章节。SN、MAC 和硬件 UID列为设备身份，不显示为参数偏差。

## 9. 实施顺序

1. 盘点各产品参数表，建立字段所有权 registry，并确认网络参数协议合同。
2. 定义 ProvisioningBundle 与参数基线 schema、导入导出和 SHA-256 验证。
3. 实现只读差异预览，使用真实设备参数表验证比较规则。
4. 实现单设备 `DeviceProvisioningCoordinator`，接入现有 OTA 与 ParameterController。
5. 实现多设备顺序调度、endpoint 身份迁移和失败隔离。
6. 实现最终出货 IP 的逐槽隔离工作流和人工门禁 fallback。
7. 接入批次、证据、报告和操作指南。
8. 完成一台、两台、断网、升级失败、参数拒绝和同 IP 出货真机验收。

## 10. 边界

- SN、MAC、硬件 UID不得由通用参数基线写入。
- 设备独有校准值在没有独立制造数据源时不得自动覆盖。
- 未通过认证解密的固件、产品/硬件不匹配固件和不受信任参数包不得进入生产模板。
- OTA 失败或返回身份不一致时不继续参数整备。
- 最终 IP 未通过隔离重连验证时，整机结果保持 `INCOMPLETE`。
- 本计划不假设设备已经支持运行时修改 IP；该能力必须以协议和真机回读证明。
