# M47 开发记录

## 用户确认与执行合同（2026-10-30）

用户确认计划后补充：SNR 超过 0 即可；例如配方静态对星 30 分钟，这 30 分钟内除开始搜星阶段外，全部 SNR 都应大于 0 才通过。

本轮以该补充覆盖初版计划中的附加锁定门槛、额外驻留秒数、累计有效时间倒计时模型：

- 配方界面已有时长为固定工况窗口，准备与硬件渐入时间独立；初始搜星计入工况时长。
- 首次正值之前允许搜星；首次正值之后任一零值、负值或无效数值永久进入该设备失败记录。
- SNR 按设备原始 ServiceFastState 有效字段逐帧消费；重复及反序时间戳保持原始证据，但不重复参与当前窗口判定。
- 3 秒设备/采样证据缺口保持窗口继续，产生证据不完整结论。共享平台反馈失效、MS 参考失效和意外设备代际变化结束共享步骤。
- 到零先停止轨迹并由反馈确认回中，再提交逐设备 PASS/FAIL/INCOMPLETE。一个设备的失败独立于其他参与者。
- 历史配方短时 `engineering_only` 元数据保持原合同；工况实际时间及 SNR 判定直接使用配方时长。

## 明确的支持边界

## 手动中止根因修复（2026-10-30 补充）

用户反馈“点中止没反应”后追踪到：点击入口同步调用运动 worker 的 wait 与夹具证据 complete；停止链路还只依赖电源回执收尾，周期刷新可以恢复按钮和覆盖进度。READY 批次入口也曾禁用中止。

新增 `ProductionAbortCoordinator` 统一持有中止请求与运动/电源退出事实，删除 `_power_abort_pending` 旁路。按钮与公开入口共用请求；先发布 STOPPING 再停止步骤推进。运动关闭、夹具证据收尾与报告归档放在后台；SDB recorder 拆出非阻塞 request_stop，主线程停止接纳后由后台等待 writer，回到主线程释放会话/Runtime 所有权。电源关闭回读和电源线程退出两个事实都成立后才完成中止；电源准备中收到中止则保持已确认关闭状态。

中止期间刷新保持按钮禁用及正在中止摘要；完成后工作流与设备卡片显示中止。失败显示原因并保留资源句柄与租约，退出等待清理完成。中止报告归档失败单独提示，保持已确认的批次中止事实。

回归覆盖真实按钮点击返回时延、Qt heartbeat 在慢速停止期间继续执行、重复点击、两种电源回执顺序、慢速运动收尾、关闭失败、准备阶段取消、停止进度出错仍关闭物理 owner，以及 READY 取消。开发中按异步回执合同更新原同步取消测试，没有放宽硬件成功判据。

## 断电创建与自动工位控制修复（2026-10-30）

用户明确创建时 DUT 必然未上电，上位机应按设备数量/电气要求自动配置电源并自行控制摇摆台。

稳定复现：先发现设备，再用 Runtime presence 过期撤销身份授权，此时创建批次的原 arm_batch_recording 返回 False。截图所示批次目录为空，符合录制授权取得前即失败的路径。修复后创建只保留未授权设备的录制意图；EndpointSessionRuntime 的 capability_identity_ready 是当前身份授权的统一事实，生产录制继续消费同一事实，权限合同保持严格。

既有设备的重新上线报文先经过唯一 Runtime，再在当前身份授权后建立录制并回填本次原始报文；不重复解析。新增回归同时覆盖 Production 先接收与 Customer/shared Runtime 先接收两种顺序，首个新身份帧均恰好保存一次。另以真实授权仍成立但录制创建失败证明 I/O 失败不会被当作离线等待而放过。

移除正式启动前人工 READY 门禁，改为上位机自动准备：电源继续按产品电压/总限流设置并闭环开启；首个需要台架的工况由 ProductionExecutionHardware 自动取得参考租约，按工位串口/波特率连接 MS，并启动所选平台控制 worker。平台回中/动态实际反馈及有效标定参考就绪后确认工况启动。共用既有控制组件、坐标标定和租约，不抢占人工调试 owner。中止/完成同时停止 MS 与平台并释放参考租约。MS worker 亦保持开始前收到的停止意图，防止重新清空取消标志。

验证覆盖：真实创建按钮接受缓存的断电设备、配置与数据库成功冻结、该阶段尚无 staging 录制文件；CONFIGURED 工位允许开始自动准备；自动控制按所选档案连接平台和 MS，回中先完成但参考帧尚未来时保持 ARMED，参考有效后进入 RUNNING。模拟硬件测试不声明物理联机、RF 或完整工况验收通过。

## 初始搜星边界根因修复（2026-10-30）

现场批次 `BATCH-20261030-1958` 的只读 SDB 与 SQLite 事件证实：旧代码在设备 uptime 32727 ms、`tracking_phase=ACQUIRING`、`locked=False`、SNR=12 时提前产生 scenario_acquired，随后在 33229 ms、仍为 ACQUIRING/未锁定、SNR=0 时产生永久失败。FINE_TRACKING 阶段也有归零；设备到 36837 ms 才明确回报 LOCKED、locked=True、SNR=12。

这说明初版把“第一个正峰”等同于“初次搜星完成”的模型错误。本节取代前文所有以首次正 SNR 作为初次完成边界的描述：现在同一有效快速状态的 LOCKED 阶段、locked=True 和正 SNR 共同确认初次完成；此前初扫/精扫的波动属于正常搜星。完成后依旧严格逐帧执行 SNR > 0，随后归零/负值永久保留为失败，不添加驻留秒数、不延长配方窗口。

Product tracking_phase 的编码映射统一到产品模型 helper，正式批次与 Product Store 共用映射。`record_snr` 纯数值入口已被类型化 `record_tracking_sample` 替代，锁定后摇摆的前置准入也使用相同完成事实。未知状态和缺失有效位保持待确认；整个窗口缺少设备阶段证据时为 INCOMPLETE。阶段呈现依据初次完成事实，不再依据当前健康样本集合回退到搜星；设备卡片各自呈现自己的阶段。

回归先在旧代码稳定复现初扫/精扫正峰后误判失败，再覆盖修复后不误判、有效位/未知/矛盾状态、进入 LOCKED 后才观察、随后重捕中的归零保持失败及恢复后不清除失败。只读回放本批次前段 1186 个快速状态，首个确认完成仍为 36837 ms，没有误报 SNR 失败，阶段为信号观测中。回放未评估完整 30 分钟窗口，未修改现场批次文件、数据库或当前运行程序的历史标记。

搜星边界修复验证：旧实现初扫/精扫正峰归零的新增回归稳定失败；修复后执行/状态机专项 25 passed，试产及 Product Store 专项 173 passed，全量 1800 passed（207.81 秒）。TS/QM 1468 条消息 check 通过。独立的 M48 布局计划/验收与效果图仅作为待确认提案，生产布局尚未变更。

## 2026-10-30 现场补修：已摇摆却停留准备阶段

### 已确认根因

用户现场批次 `BATCH-20261030-2046` 的只读记录显示：

- 首个 `trajectory_point` 的单调时钟为 `511762964698625 ns`；配方渐入为 5 秒。
- 首轨迹后约 `2.684546083 s` 的最后有效参考帧航向标准差约 `0.9722°`；其后超过工位 `max_attitude_std_deg=1.0°`。5～6 秒窗口的航向标准差约为 `1.42°～1.58°`。
- 平台脉冲持续变化，控制器反馈和轨迹发送记录持续到达，批次 attempt 却始终为 `armed/preparing`，没有启动回执。
- 原 `_confirm_start` 在参考质量不足时直接返回；领域准备轮询将具体条件覆盖成统一等待文案；Runtime 只在有效参考时写 READY，质量失效未撤销该状态。因此形成“平台在动、MS 绿灯、准备原因不明、倒计时固定”的一致复现。

### 修复和验收

- 由硬件执行 owner 统一给出参考质量原因，分别说明导航状态、姿态值、标准差无效/超限与参考过期。Runtime 灯和执行准入读取同一事实；参考质量超限/过期呈现 CONNECTED，保留实际值和工位上限，绿色就绪只代表有效参考。
- 准备阶段展示连接、回中、关电回读、轨迹发送、渐入、运动反馈或 MS 参考的实际条件；业务计时仍由正式启动证据开启。
- 已确认实际位移并经过渐入后，参考不满足要求则进入 INCOMPLETE 并使用现有硬件/电源/证据收尾；动态上电在同一门禁前校验，超限时不向 DUT 请求开启输出。初始参考连接与静态参考等待保持原合同。
- 不修改工位 1° 上限，不以正 SNR 代替 MS 参考资格，不追补现场未被正式观察的时间，也不修改用户批次数据库或配置。
- 新增 `test_production_reference_start_gate.py`：现场渐入时序、无效灯/标准差原因、有效参考与真实发送锚点倒计时、动态上电门禁、过期参考共 5 项通过。最终完整回归 **1889 passed（218.95 s）**；翻译 update/check 通过（1462 项），差异空白检查通过。

现场只读取现有 CSV/JSONL/SQLite；没有连接电源、摇摆台或串口执行命令。当前已运行进程保持原加载代码；修复需要重启源码后创建新批次验证。

## 2026-10-30 现场补修：MS 与 DUT 共用电源

用户明确 MS-6222 也由同一受控电源供电。批次 `BATCH-20261030-2119` 配方启用 power_on_rocking，SQLite 原因是 `Waiting for fresh MS-6222 reference`，电源汇总回读为关闭。旧时序在主动断电后继续以 MS 数据作为轨迹准入/恢复供电条件，导致断电造成的预期数据缺口触发 INCOMPLETE 和关电收尾。

根因修正位于硬件执行 owner：

- `PowerOnRockingPhase` 统一拥有断电请求、断电回读、上电请求、参考采集恢复、正式观察阶段；主动断电阶段与普通观察阶段有明确边界。
- 发出断电请求前清除参考准入并受控停止当前串口 reader；共享电源关闭后，平台真实脉冲变化、反馈新鲜度和渐入条件足以请求上电，MS 数据不参与该恢复供电条件。
