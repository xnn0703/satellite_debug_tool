# M42 用户版与运维版拆包计划

状态：2026-10-23 用户明确修订：用户版保留现有 Shell（TCP、串口及 YMODEM），已完成该范围的源码修订与 macOS 双版验证。

需求：面向客户交付轻量用户版，运维版保留现有全量功能。按用户提供的 AGENTS.md 工作流，先固定本计划与[验收标准](M42_user_operations_editions_acceptance.md)，再实施并维护[开发记录](M42_user_operations_editions_dev_log.md)。

客户设备仍按现有显式 IP/端口方式添加，自动发现属于独立需求。

## 二、拆包前源码事实

1. `main.py` 只有一个入口，接受 `--production`；`MainWindow` 导入工程、试产和 FixtureRuntime，并注册 E/P 解锁快捷键。
2. `CustomerWorkspace._PAGE_DEFS` 包含总览、RF、iperf、回放、维护；Shell 与摇摆台也是客户侧现有入口。
3. `CustomerEndpointSessionBundle` 创建客户绑定时会创建外接电源和 iperf 控制器。页面数量缩减之后，还要同步收敛这些 owner 的创建和生命周期。
4. `satellite_debug_tool.spec` 全量收集应用子模块与 PySide6、OpenGL、docx 等依赖；用户总览的 3D 姿态仍依赖 OpenGL，图表仍依赖 numpy/pyqtgraph。
5. 现有更新资产过滤只按 `-win-...7z` 等平台模式匹配，并取排序后的第一项；双版本发行必须建立版本类型合同。

## 三、实现结构

### 3.1 一套源码、两个构建产物

- 共享协议解析、设备会话、目录、Store、录制/回放数据格式与客户 RF 领域逻辑，保持一个设备事实来源。
- 建立明确的 user/ops 装配入口与构建身份；构建身份由打包产物携带，界面只呈现当前产物允许的能力。
- 用户入口只装配客户页及其必要 owner，运维入口装配完整工作区与工具。
- 将运维专属 import 从客户公共装配路径分离；按产物过滤收集与排除模块，审查最终依赖图。
- 用户版接受日常客户设置；工程/试产解锁快捷键、`--production`、旧设置与直接页面入口均保持用户版能力边界。
- 这是产品装配边界，现阶段范围为本应用的入口、模块和分发合同，保持单一领域实现。

### 3.2 轻量化的验收方式

- 用户包排除运维专属页面、夹具/电源/iperf 执行模块、试产报告生成及其专用资源。
- 共享协议、历史文件读取所需的纯数据模型继续复用；历史 SDB 中的夹具记录可以被兼容读取，控制模块的归属仍由产物装配决定。
- 根据真实导入路径评估 python-docx、pyserial 和加密 OTA 密钥/依赖的裁剪；客户 3D、曲线等保留能力所需的 Qt/OpenGL/numpy 继续提供。
- 按两版包体积、启动耗时、空闲内存、后台 owner/线程与最终模块清单提供实测对照；本计划以实际构建结果确定轻量收益。

### 3.3 安装、设置与更新

- 两版安装目录、macOS bundle identity、应用内版本类型标识明确区分；公共产品名继续保持中性。
- 运维版延续当前全量版的设置与升级归属；用户版拥有独立设置、更新暂存和事务状态目录。
- 用户版首次使用空设备目录，设备由用户显式添加；现有全量版配置继续由 ops 原路径读取，保留原有用户数据。
- 历史全量版按 ops 处理。现有 EXE/载荷名称与旧 updater 合同在运维迁移边界内保持可识别。
- 新更新器按 edition/platform/version 精确选择资产，在下载与安装前验证产物身份；user 只安装 user，ops 只安装 ops。
- 用户包使用旧更新器平台正则无法命中的独立资产命名；现有旧名称继续指向全量 ops。发布前冻结最终资产矩阵与旧更新器迁移版本边界，并回归旧客户端的匹配行为。
- 应用版本号继续以 `__version__` 为单一来源，两版由同一次源码版本构建。

## 四、实施顺序与交付

1. 范围已确认，用户版保留独立固件升级；按最终页面/能力矩阵执行。
2. 固定 edition 身份、公共装配接口、配置目录及更新资产/载荷合同。
3. 分离客户公共依赖与运维装配，完成用户版四页面与运维版全量装配。
4. 调整 Windows/macOS 脚本、spec、CI 构建矩阵与发行资产检查；构建并比较实际产物。
5. 执行两版功能回归、用户版边界检查、更新交叉拒绝测试、包内容审计与原生窗口烟测。
6. 对照验收文档更新开发记录、AGENTS.md、BUILDING.md 和 RELEASING.md，形成可审查交付。

本计划已完成源码实现与 macOS 本地构建验证；Windows 冻结运行与真实设备验收保持待验。提交、版本发布与远程发布按用户后续指令执行。


## 2026-10-23 Shell 范围修订

用户明确要求“用户版本的 shell 还是要保留的”，据此直接修订已确认的双版本范围。用户版四页面保持现状，并提供侧栏 Shell 弹窗；完整复用现有 TCP、串口终端、YMODEM 和受管理 endpoint 的事务网关。Shell 在首次打开时创建，连接由用户发起；关闭和应用退出沿用同一收尾路径。

本轮步骤：先增加用户版入口/弹窗/包内容回归；恢复公共 Shell 入口与模块白名单，保留其他运维模块边界；按版本根目录保存 Shell 会话证据；重新构建两版并验证冻结 Shell 弹窗、语言/主题、签名及正常退出，更新包体积与验收记录。Windows 构建及设备 Shell/YMODEM 实测按对应平台/硬件门禁执行。


## 2026-10-23 用户版总览缺失面板修复计划

用户截图确认 SNR 曲线和底部模块温度均未显示。源码证据：`CustomerOverviewView._setup_ui()` 将两个公共面板加入 root layout 的语句及初始密度设置误缩进至 `enable_external_power` 条件内；user 的该条件为 False，两个面板已构造却未加入可见布局。

修复范围：SNR 与三模块温度始终作为公共总览布局组成；外接电源条件仅负责其自身锚点。保持原数据 Store、SNR 五分钟窗口及温度来源。先新增 enable_external_power 两档及连接/未连接回归复现，再修正所属布局分支；同时强化真实用户入口与冻结烟测的面板装配检查，重新生成本地双版包并审查截图。
