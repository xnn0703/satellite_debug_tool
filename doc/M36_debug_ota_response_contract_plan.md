# M36 旧固件 OTA 响应合同迁移计划

## 1. 问题与根因

AFD01C `0.0.130_beta` 的 OTA 固件实现返回通用 `COMMAND_RESPONSE` 文本：

- `OTA_BEGIN` 成功：`OK`
- `OTA_DATA` 成功：`OK`，重复分片：`dup OK`
- `OTA_END` 校验成功：`OK, rebooting`

当前上位机依照 DEBUG v2 规范只接受 `OTA_BEGIN=READY`、`OTA_DATA=<seq>`、
`OTA_END=VERIFIED`。设备返回的通用成功响应不会推进状态机，因此发送
`OTA_BEGIN` 后在 15 秒处显示超时。

## 2. 单一正式合同

固件的 `debug_ota.c` 改为始终返回带操作上下文的结果：

- BEGIN 成功：`OTA_BEGIN=READY`
- BEGIN 失败：`OTA_BEGIN=<原因>`
- DATA 成功或确认重复分片：`OTA_DATA=<实际序号>`
- DATA 失败：`OTA_DATA=<实际序号>`，响应码表达失败类型
- END 校验成功：`OTA_END=VERIFIED`
- END 失败：`OTA_END=<原因>`

上位机严格模式继续只消费当前阶段、当前序号的响应。该模式是修复后固件的唯一正式合同。

## 3. 旧固件引导边界

现有旧固件无法通过 OTA 获得正式合同，因此上位机为明确的旧版本增加一次迁移路径：

- 仅限已认证解密的客户包、已注册 AFD01 系列产品，且当前设备固件版本低于首个修复版本。
- 仅在 OTA 独占设备事务、已停止 Debug 数据并暂停握手请求后启用。
- BEGIN 只接受成功码加 `OK`；DATA 只接受成功码加 `OK` 或 `dup OK`；
  END 只接受成功码加 `OK, rebooting`。
- 任意失败码直接结束对应阶段，向界面显示设备原因，不等待超时。
- 当前阶段之外的带上下文响应、其他文本和迟到响应不推进状态机。
- 设备升级并回读到首个修复版本或更高版本后，只使用严格合同。
- 首个修复版本确定后固化为常量，并在代码、文档和测试中保留退出条件。

## 4. 实施范围

### 固件仓库

- 修改共享 `debug_ota.c` 的响应生成，不改变 OTA 命令号、分片格式、CRC 或存储流程。
- 通过受影响目标构建和代码审查验证 BEGIN、DATA、END 成功、拒绝、重复分片及 CRC 失败路径。
- 生成高于 `0.0.130_beta` 的 AFD01C 测试固件包作为迁移目标。

### 上位机仓库

- 在 `OtaController` 内建立由“当前设备型号 + 当前固件版本”决定的响应合同；UI 不持有该事实。
- 对旧固件通用响应进行阶段内精确映射；修复版本及以后保持现有严格匹配。
- 在 OTA 状态区记录本次使用“旧固件引导合同”或“严格合同”。
- 应用日志记录发送阶段、接收响应码和文本、合同模式及最终终态，不记录固件明文。

## 5. 不变边界

- `.sfpkg` 的 AES-GCM 解密、SHA-256、产品白名单和版本策略不变。
- Shell/网络 YMODEM 的传输状态机、ACK/NAK、候选区写入、`raw_fw`、Boot 安装与恢复入口不变；
  本次固件修改只调整 DEBUG v2 `COMMAND_RESPONSE` 文本。
- `allow_downgrade` 只控制选包准入，不代表设备已接收 OTA。
- `OTA_END=VERIFIED` 或旧合同 `OK, rebooting` 只证明设备接受并校验传输内容；
  安装完成仍由同 endpoint 回机身份和目标版本回读确认。
- 不通过加长超时、盲目重试或忽略响应内容解决该问题。

## 6. 实施顺序

1. 固件响应合同修正与单元测试。
2. 上位机旧版本迁移边界与回归测试。
3. 回归 YMODEM 接收、候选校验、安装和 Boot 恢复路径。
4. 更新 DEBUG v2 规范、操作指南和开发日志。
5. 构建 AFD01C 修复版本测试包。
6. 使用 `0.0.130_beta -> 修复版本` 完成真机迁移；再用修复版本验证严格合同。
