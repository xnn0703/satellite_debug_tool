# M58 摇摆台连续运动、组合包线与预录制可靠性计划

## 1. 目标

本轮处理三项现场问题，并保持一个业务事实只有一个权威 owner：

1. 连续摇摆由运动组件拥有稳定的命令时间线，界面绘图负载不再影响控制节拍。
2. 三轴组合轨迹由完整路径逆运动学拥有可达性结论；单轴角度规格与组合姿态可达性分别呈现。
3. 预录制意图与 recorder 由 endpoint Runtime 拥有；设备上线、身份建立和完整采集协商成为录制内的质量阶段。

## 2. 已确认的现场证据

### 2.1 20 ms 连续轨迹的发送空洞来自上位机

`/Users/xmac/Desktop/摇摆台.pcapng` 中第二轮轨迹包含 9,122 条 33 字节位置命令，命令内完成时间均为 20 ms。控制器反馈同时保持稳定：

| 证据 | 结果 |
|---|---:|
| 轨迹命令间隔中位数 | 20.339 ms |
| 轨迹命令间隔 P95 / P99 | 26.958 / 34.055 ms |
| 间隔大于 40 / 50 ms | 52 / 31 次（排除会话结束后的中心命令） |
| 轨迹内最大命令间隔 | 73.225 ms |
| 最后约 15 s 的 P95 / P99 | 约 43 / 62 ms |
| 控制器反馈间隔中位数 / P99 / 最大值 | 21.000 / 21.197 / 21.388 ms |
| 控制器状态 / 命令结果 / 伺服错误 | `state=4` / `C0,0` / 六轴 0 |

夹具会话 `20261103T054212-c30fdf1b` 另行记录 9,122 个已发送轨迹点和 110 个跳过点。当前 `maximum_lateness_ms=19.908` 在跳点后重新计算 deadline，因此没有表达抓包中的 73.225 ms 实际发送空洞。

当前页面每 100 ms 重建最长五分钟的 Target / MS 实测 / Error 九条曲线；MS 数据约 200 Hz，两个 30,000 项显示 deque 在约 150 s 后进入满载滚动。抓包中的节拍恶化集中在约 170 s 后，与主线程持续处理大曲线和高频遥测的负载增长一致。该调用链与 Python 线程共享 GIL，属于当前最强的软件根因证据；物理卡顿仍由修复后的真机复测确认。

### 2.2 `15°` 是组合姿态越界，不是显示角度被放大

现场会话先提交三轴 15°，随后提交同参数的三轴 14°。把成功执行的 14°轨迹逐点按 `15/14` 放大后，第一项不可达姿态为：

```text
Roll  = -14.1132115°
Pitch = -14.1132115°
Yaw   = -13.4910788°
axis 4 extension = -0.21 mm
```

这与 13:43:43 的现场错误逐字一致。14°轨迹的最小执行器余量只有 0.51 mm，因此 14°处于当前几何合同的边缘。

图片中的 Roll/Pitch/Yaw `±30°` 是厂家单项规格。当前权威几何来自厂家 `plat.xml` 与 DLL 对拍：430/600 mm 平台直径、425 mm 固定杆、0..200 mm 伸长量。单项角度上限不能推导出任意三轴组合都可达。严格整条拒绝保护了刚体姿态；旧厂家软件的逐缸钳位曾造成堵转，不能恢复。

当前缺陷位于呈现合同：页面只按三个单轴 `±30°` 设置输入范围，预览只检查角度、频率、速度和加速度；完整路径逆解在 worker 接单后才执行，所以界面先显示“轨迹校验通过”，随后控制请求失败。

### 2.3 预录制当前从完整采集回执后才创建文件

当前状态流为：

```text
ARMED → 设备 ONLINE → PREPARING → SET_CAPTURE_PROFILE=support_full 回执
      → 创建 DataRecorder → ACTIVE
```

因此首个设备数据、身份建立和完整采集协商均发生在 SDB 创建之前。首次协商发送失败、超时、拒绝或能力暂未建立时，现有分支还会进入恢复并最终清除录制意图。这个模型直接解释“上线后自动退出预录制”和启动数据缺失。

## 3. 设计

### 3.1 连续运动时间线

1. `core/motion_platform/` 继续作为 UDP、运动学、轨迹和反馈的唯一 owner。
2. 连续轨迹使用一项明确的现场资格合同：采样周期、命令完成时间和允许发送间隔共同冻结；前一命令的运动时间必须覆盖下一命令的实际到达时间。
3. 先以厂家已验证的 50 ms 连续发送合同作为现场验证起点；20 ms 标记为“待资格确认”，不再仅凭型号最短单次动作时间推导为连续轨迹能力。
4. 页面曲线改为有界查询和像素预算下采样。每次刷新处理量由视口像素和固定窗口决定，不随会话累计样本增长。
5. 调度结果直接记录实际相邻发送间隔、最长控制空洞、超期点和控制时间线结论。跳点后仍保留原空洞证据。
6. 达到时间线故障条件时，状态机发布明确的 timing fault。M60现场复测后，可恢复迟到继续当前点并从真实发送时刻重建周期；显式停止与UDP发送错误才结束发送。
7. 若 50 ms + 有界呈现仍无法满足时间线合同，再将运动 UDP 与轨迹调度迁移到独立进程。该升级由同一验收数据触发，不并存第二套发送 owner。

### 3.2 三轴组合包线

1. 新增唯一的 `TrajectoryPreflightResult`，同时包含角度/频率/速度/加速度和逐点六缸行程结论。
2. UI 预览和 worker 启动消费同一结果；worker 只接受结果绑定的不可变轨迹摘要，避免预览后参数漂移。
3. 输入框继续显示型号单轴规格；组合区明确显示“单轴规格不代表任意三轴组合可达”。
4. 预览显示限制轴、限制姿态、最小/最大伸长量与余量。不可达轨迹停留在预览阶段，不进入 busy 或发送状态。
5. 保留严格整条拒绝；不增加逐轴钳位、角度缩放或设备特例。

### 3.3 预录制生命周期

1. 用户点击预录制后立即创建 SDB v3 recorder，并把 recorder lease 绑定到 endpoint Runtime。
2. 初始 header 使用已知 endpoint 和明确的待确认身份；首个 UDP 数据从 recorder 建立后立即写入。
3. 设备身份、能力和 `support_full` 回执以类型化 metadata 事件写入同一文件；身份确认后不重建 recorder。
4. 录制状态与采集质量拆分：`RECORDING` 表示字节正在持久化，`WAITING_DEVICE / NEGOTIATING_FULL / FULL / PASSIVE` 表示采集阶段。
5. 设备上下线与 telemetry epoch 只推进录制内阶段。用户停止/取消、存储失败和应用受控退出才结束 recorder。
6. 每个在线代际只依据新的身份与能力证据发起一次完整采集协商。新在线代际允许新的协商，不使用定时盲重试。
7. SDB summary 分别保存原始录制连续性和完整采集覆盖区间；完整采集未建立时结论保持明确的 `PASSIVE/INCOMPLETE`。

## 4. 实施顺序

1. 增加三项稳定复现：20 ms 后段负载、15°组合越界、预录制上线协商失败。
2. 收敛组合轨迹预检模型和 UI 呈现。
3. 将预录制意图及 recorder 生命周期迁入 endpoint Runtime。
4. 将夹具曲线改为有界投影，并补齐真实发送间隔证据。
5. 执行定向测试、全量 pytest 和翻译 update/check。
6. 在真实摇摆台执行 50 ms 连续轨迹抓包与 MS-6222 对照；20 ms 作为独立资格项。

## 5. 交付边界

- 软件自动化证明状态流、预检、数据连续性和发送时间线统计正确。
- 抓包证明工作站 UDP 发送节拍与控制器反馈事实。
- MS-6222 证明平台实际姿态幅值、频率和短时连续性。
- 机械安全、负载下平顺性、急停和长期寿命继续使用现场独立验收。
