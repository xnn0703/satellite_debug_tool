# M19-A.11 灵境运动平台直接控制组件实施计划

## 1. 目标

- 将灵境平台的 UDP 传输、控制器协议、运动学、状态机、轨迹调度和诊断证据实现为独立组件。
- 由控制器实时反馈确认“已到位”“回原点完成”和故障状态，替换当前“命令已发送后按预计时长结束”的模型。
- 试产夹具测试、摇摆台自动测试和后续动态场景仿真只调用组件公开接口，不直接操作 socket、协议帧或厂家服务程序。
- 直接控制组件成为运动平台的唯一权威 owner；同一进程、同一平台只能存在一个活动控制会话。

## 2. 已确认事实与实施边界

### 2.1 已确认

- 控制器命令端点为 `192.168.15.201:7408`，本机反馈端点为 `192.168.15.101:8410`。
- 位置控制使用 33 字节 `0xC0` 帧，反馈使用 68 字节帧；正常反馈周期约 20 ms。
- 回原点命令为 `AA 55 00 01 03 FB FB`，回原点期间允许出现两段长反馈中断，最终需要重新进入 CSP 运行态。
- 超范围姿态在厂家实现中会逐轴钳位到 200 mm，并可能造成 `0x7121 Motor blocked` 或 `0x6320 Parameter error`。该行为不能作为安全限位继续使用。
- 物理急停会使控制器重启，表现为反馈中断、序号和控制器时间回退、状态重新迁移；抓包中没有独立的软件急停命令。
- 当前供应商程序没有可用的取消定位和软件快速停止入口，反馈中也没有可证明的硬限位状态字段。

### 2.2 本里程碑不声明的能力

- 不把停止后不再发送轨迹点称为急停或快速停止。
- 不声明已具备硬限位、软件急停、取消定位或任意伺服故障自动恢复。
- 不在运动平台组件内耦合 MS-6222。MS-6222 作为独立姿态参考，由上层联合测试或闭环控制器显式组合。
- 不以 UDP 写入成功、控制器 `reccmdret=0` 或预计运动时长作为物理到位证据。

## 3. 组件结构

在 `satellite_debug_tool/core/motion_platform/` 建立与试产 UI 无关的领域组件：

```text
core/motion_platform/
  __init__.py
  models.py              # 配置、姿态、快照、能力、动作结果和肯定式状态
  lingjing_protocol.py   # 严格运动学、命令编码和反馈解码
  controller.py          # 唯一 socket/thread owner 与控制器状态机
  trajectory.py          # 轨迹预检、单调时钟调度和反馈闭环完成
  evidence.py            # 命令、反馈、状态迁移和故障证据输出
```

公开接口只表达领域意图：

- `connect()` / `close()`
- `home()`
- `move_to(pose, motion_profile)`
- `run_trajectory(trajectory)`
- `stop_trajectory()`
- `recover_to_center()`
- `snapshot()`、状态/反馈/事件信号

UI、试产批次和自动测试不得导入 `lingjing_protocol.py` 或直接访问 UDP socket。

## 4. 单一状态模型

组件状态采用肯定、单义的事实：

- `OFFLINE`：当前没有新鲜控制器反馈。
- `STARTING`：已建立本地传输，正在等待控制器有效反馈和运行态。
- `READY`：当前连接代际内收到新鲜反馈，控制器处于 CSP 运行态且六轴无故障。
- `HOMING`：已发送本次回原点命令，正在观察本次回原点状态链。
- `MOVING`：本次单点目标已发送，正在依据六轴反馈判定到位。
- `TRAJECTORY`：已完成整段轨迹预检，正在按绝对单调时钟发送采样点。
- `RECOVERY_REQUIRED`：控制器重启、急停恢复、反馈代际变化或动作期间断网后，需要显式恢复。
- `FAULT`：当前反馈包含伺服错误或协议/运动学安全错误。

动作完成必须同时满足：

1. 反馈属于发令后的当前连接代际；
2. 六轴实际位置均进入配置的到位容差；
3. 连续稳定时间达到配置值；
4. 控制器处于运行态；
5. 六轴错误码均为零。

回原点完成必须观察到本次 `0x03` 命令后的回原点状态链、恢复运行态、目标附近稳定反馈和无故障；回原点专用超时允许覆盖已捕获的长反馈中断。

## 5. 安全与运动合同

### 5.1 严格预检

- 姿态超过型号配置的 Roll/Pitch/Yaw/位移边界时，整条命令被拒绝且不发送任何帧。
- 逆运动学计算出的任一执行器长度超出 `[0, 200] mm` 时，整条命令被拒绝；删除逐轴钳位路径。
- 轨迹启动前计算并校验全部采样点；任一点无效则整段拒绝，避免执行到中途才发现越界。

### 5.2 丝滑轨迹

- 使用连续位置、速度和加速度边界的轨迹生成器；正弦轨迹直接按相位方程采样。
- 默认以控制器已验证的 20 ms 周期调度，使用绝对单调时钟 deadline，禁止用串联 `sleep(period)` 累积漂移。
- 迟到的采样点按策略跳过到当前相位，禁止瞬时补发形成突发命令。
- 每个采样点仍经过整个平台运动学预检；末点由反馈闭环确认完成。

### 5.3 停止与恢复

- `stop_trajectory()` 只表示停止产生后续轨迹点，并把状态转换为反馈确认的受控停止过程。
- 只有反馈新鲜且当前姿态可解时，才允许执行显式 `recover_to_center()`。
- 任何伺服错误使当前动作失败并进入 `FAULT`；普通运动命令保持关闭，恢复必须由显式恢复操作触发。
- 反馈序号或控制器时间回退视为控制器重新启动，当前动作失效并进入 `RECOVERY_REQUIRED`。
- 现场紧急停止继续使用平台物理急停回路。

## 6. 型号档案与迁移

夹具档案升级到新 schema，并由型号预置以下直接控制参数：

- 稳定 `model_id`；
- 本机绑定 IPv4 `192.168.15.101`、反馈端口 `8410`；
- 控制器 IPv4 `192.168.15.201`、命令端口 `7408`；
- 平台几何参数、执行器长度范围和姿态范围；
- 到位容差、稳定时间、反馈新鲜度、普通动作超时和回原点超时；
- 协议版本和几何参数 SHA-256。

旧版档案按稳定型号迁移到新预置。旧档案中的厂家服务地址 `192.168.15.101:9800` 不解释为控制器地址。未知型号进入“待确认”，不允许运动。

## 7. 集成与旧实现移除

1. `ProductionWorkspace` 创建并注入一个运动平台组件实例。
2. 夹具调试页、摇摆台自动测试和正式批次只通过公开接口提交意图并订阅快照。
3. `FixtureControlLease` 继续作为进程级排他所有权入口，组件内部再保证 socket 与动作串行化。
4. UI 显示连接代际、控制器状态、六轴目标/实际位置、误差、错误码和反馈年龄。
5. UI 只有在反馈闭环满足完成条件后显示“已到位”或“回原点完成”。
6. 直接控制路径通过测试后，删除当前厂家服务启动、A6/A6T 转发、进程托管、打包资源和对应旧测试；发行包不再携带或自动启动厂家服务程序。
7. 删除 `core/production/lingjing_controller_protocol.py` 的旧位置和兼容导入，协议实现只保留一个 owner。

## 8. 诊断与证据

每次控制会话保存：

- 组件配置、型号档案 revision 和 SHA-256；
- 原始发送帧、原始反馈帧、解析后的六轴位置和状态；
- 状态迁移、连接代际、序号/时间回退、调度迟到与丢点；
- 每个动作的目标、预检结果、发令时间、到位时间、最大误差、失败原因；
- 回原点、断网、故障和恢复事件；
- 软件版本与会话 manifest。

这些证据通过稳定的数据模型接入现有夹具诊断 ZIP，不能依赖 UI 文案反向解析。

## 9. 实施顺序

1. 建立组件模型和固定协议向量测试。
2. 将运动学改为严格拒绝，并增加 Roll 32° 不发送回归测试。
3. 实现单 socket owner、反馈接收、连接代际和状态机。
4. 实现反馈闭环单点动作、回原点和恢复动作。
5. 实现轨迹全量预检与 20 ms 绝对时钟调度。
6. 接入诊断证据、型号档案迁移和配置导入导出。
7. 替换夹具 UI、自动测试和正式批次调用链。
8. 删除厂家服务活动路径、资源和打包钩子。
9. 更新翻译资源、用户文档、AGENTS 架构说明和开发日志。
10. 完成自动化回归、Windows 打包和现场分级验收。

## 10. 现场验收边界

- 首次真机只执行连接、静止反馈、回中、Roll/Pitch/Yaw 单轴 `±1°`、低幅三轴正弦和回原点。
- 验证断网重连与物理急停后的 `RECOVERY_REQUIRED`，由人工确认安全后执行恢复。
- 不再用 Roll 32° 制造越界故障；越界在发送前由自动测试证明被拒绝。
- MS-6222 同步记录用于核对方向、响应和精度，但不作为本里程碑运动命令的实时闭环输入。
