# M68 平台相关连续轨迹周期计划

## 1. 根因证据

- 供应商 Windows 上位机有效抓包中，三轴组合摇摆连续发送 527 条位置帧，命令周期和帧内完成时间均为 50 ms。
- 控制器反馈周期约 21 ms；反馈周期属于控制器状态流，不能解释为上位机位置命令周期。
- M61 将本项目夹具会话对应的 `摇摆台.pcapng` 误记为厂家原上位机抓包，并据此把 20 ms 冻结为跨平台合同。
- macOS 20 ms 路径已经完成现场运行验证；Windows 采用供应商已验证的 50 ms 合同，不再通过云端 runner 重试推导物理时间能力。

## 2. 单一模型

1. 运动领域层是平台周期的唯一 owner：macOS 固定 20 ms，Windows 固定 50 ms。
2. `SineTrajectory`、预编译帧、指纹、生产配方、报告和界面只消费当前平台的周期投影，不提供人工周期入口。
3. Windows 发送进程采用有界休眠和末段非阻塞命令轮询，不使用全程忙等待。
4. 迟到仍保存 `timing_fault`，发送当前点并从真实发送时刻建立下一周期；不跳点、不突发追赶。
5. 组合姿态包线继续使用 20 ms 计算分辨率；该分辨率只服务运动学安全，不改变 Windows 50 ms 命令周期。

## 3. 验证

1. 单元测试证明 macOS 解析为 20 ms、Windows 解析为 50 ms。
2. 当前平台的协议帧、预编译点数、缓停点数、生产配方和报告均使用同一周期。
3. Windows Actions 验证完整发送、顺序、无跳点、无重复发送 owner、迟到留痕和无追赶；共享 runner 不承担物理平台节拍验收。
4. macOS 保留 20 ms 现有软件和现场证据；Windows 后续在真实工位以 pcap、控制器反馈和伺服错误完成现场验收。
5. 定向回归、翻译检查和全量 pytest 通过后才允许重新发版。

## 4. 证据边界

- 软件测试证明平台策略选择、数据流、发送语义和证据记录。
- Windows 真实时间线、机械平顺性及控制器状态只能由真实 Windows 工位和摇摆台证明。
- 供应商程序提前完成、逐缸钳位和缺少软件停止的缺陷不进入本项目模型。
