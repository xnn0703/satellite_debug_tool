# M19-A.10 灵境平台服务静态分析结论

## 1. 结论

`ProConvert.exe` 和 `StewartPlat.dll` 已足以独立复现以下部分：

- A6/A6T 文本命令解析后的六自由度逆运动学；
- 当前 `plat.xml` 的几何参数、零位高度、杆长、行程钳位和脉冲换算；
- PC 到控制器的 UDP 位置指令帧；
- 控制器到 PC 的状态、路径计数、命令结果、六轴位置和伺服错误码反馈帧。

已建立纯 Python 离线原型，并由原始 `StewartPlat.dll` 本体对拍通过。原型没有网络发送接口，不会控制真实平台。

当前还不能替换厂家服务用于正式真机控制。控制器固件仍独占 EtherCAT/CiA402 状态机，以下合同没有文档或真机证据：

- `systemstate` 各状态的实际进入和退出条件；
- `reccmdret` 成功、拒绝和故障值；
- 位置帧被接收、进入队列、完成和机械到位之间的关系；
- 力矩回零、位置模式使能、快速停机、取消定位的现场语义；
- 急停、限位、伺服故障、断网和恢复时的控制器行为。

因此当前判断为：**运动学和控制器线协议可以自行实现；安全状态机和完成合同待真机确认，暂不替换现有厂家服务。**

| 路线 | 判断 | 依据 |
|---|---|---|
| 纯 Python 直接实现 | 后续目标 | 运动学、0xC0 编码和反馈解析已与原 DLL 对拍；可以建立明确的状态 owner |
| C# 无界面 helper | 可做但没有架构收益 | DLL 公共 API 可调用，但动作完成和安全恢复缺口仍然存在，并继续引入 .NET 与厂家 DLL |
| 继续托管厂家服务 | 当前正式路径 | 已完成 Windows 集成且可驱动真机；在控制器状态合同冻结前风险最低 |

## 3. 调用链

### 3.1 应用层

```text
上位机
  -> UDP 192.168.15.101:9800
  -> ProConvert HostClass
  -> Platform.ProcessCmd("@A6T:...")
  -> Platform.RunEura
  -> Platform.Do_IK
  -> ECMPlatform.MoveServo
```

厂家协议 V0.3 明确 UDP 默认端口为 9800，并规定 A6 参数为 Roll、Pitch、Yaw、X、Y、Z；A6T 在末尾增加完成时间毫秒数。该协议同时明确需要在 PC 上运行指定控制软件，不能把文本命令直接发送到平台板卡。

### 3.2 控制器层

```text
ECMPlatform
  -> 本地 UDP 0.0.0.0:8410
  -> 目标 UDP 192.168.15.201:7408
  -> 0xC0 位置帧
  <- 控制器反馈帧
  <- 状态、路径计数、命令结果、六轴脉冲、六轴伺服错误码
```

诊断包显示同一厂家进程 PID 同时监听 UDP 9800 和 8410，Windows 工作站同时配置了 `192.168.1.22` 与 `192.168.15.101`。

## 4. 运动学与参数

软件内权威 `plat.xml` 参数为：

| 参数 | 值 |
|---|---:|
| 上平台外接圆直径 / 短边 | 430 mm / 50 mm |
| 下平台外接圆直径 / 短边 | 600 mm / 50 mm |
| 固定杆长 | 425 mm |
| 最大伸长量 | 200 mm |
| 电缸每毫米脉冲数 | 1000 |
| 电子齿轮比 | 39.5 |
| 计算零位高度 | 360.29 mm |

换算顺序已由 IL 和 DLL 对拍确认：

1. 根据上下平台几何生成六对连接点；
2. 用 Roll/Pitch/Yaw 的旋转矩阵和 X/Y/Z 平移计算六根杆总长，并保留两位小数；
3. 伸长量等于总长减固定杆长；
4. 伸长量钳位到 `0..200 mm`；
5. 脉冲为 `round(1000 × 伸长量 × 39.5)`。

组合姿态 `Roll=3°、Pitch=-2°、Yaw=1°、X=Y=0、Z=50 mm` 的 DLL 对拍结果为：

```text
总长(mm): 480.66, 475.24, 460.07, 455.15, 469.45, 468.44
脉冲:     2198570, 1984480, 1385265, 1190925, 1755775, 1715880
```

## 5. 控制器线协议

### 5.1 位置命令

六轴 `0xC0` 帧共 33 字节：

```text
AA 55 | payload_len:u16_be | C0 | duration_ms:u16_be
      | axis_1..axis_6:int32_le | FB FB
```

上面组合姿态、完成时间 50 ms 的 DLL 原始输出为：

```text
aa55001bc000322a8c2100e0471e00312315000d2c12007fca1a00a82e1a00fbfb
```

Python 原型逐字节生成相同结果。

### 5.2 反馈帧

六轴反馈帧为 68 字节，无独立长度字段：

```text
AA 55
id:int32_le
controller_time:uint32_le
systemstate:u8
idlepathcnt:u8
allpathcnt:int32_le
donepathcnt:int32_le
fifocnt:int32_le
fifoindex:int32_le
reccmd:u8
reccmdret:u8
axis_position[6]:int32_le
servo_error[6]:uint16_le
FB FB
```

离线原型覆盖噪声前缀、分片、粘包、轴数锁定、帧尾校验、负脉冲和错误码保持。相同固定帧送入原 DLL `ClassFeedback` 与 Python 解析器后，所有字段一致。

## 6. 厂家程序暴露出的状态缺口

- UDP 发送成功只返回 socket 写入结果，不证明控制器接受或执行。
- 厂家服务收到 A6/A6T 后会把自身业务状态恢复为“就位”，没有等待控制器完成。
- `IsOnPos` 只比较反馈脉冲与目标脉冲，容差 250 脉冲；厂家服务没有把该结果反馈给当前上位机。
- `@stop` 只改变厂家进程内的命令接收状态；当前 `ECMPlatform` 没有覆盖 `StopPlat`，因此该路径没有向控制器发送快速停机。
- 枚举中存在系统暂停、力矩回零、位置模式使能、快速停机和取消定位命令，但当前服务只明确调用了力矩回零。
- 反馈定义包含完整控制器状态和伺服错误码，但厂家服务没有把它们转换成可审计的动作完成或故障恢复状态机。
- 当前 EtherCAT 驱动是托管 UDP/TCP 代码；大量 `zauxdll.dll` P/Invoke 属于另一个未启用的 Zmotion 驱动，不是当前 ECMEthcat 的依赖。

当前 ECMEthcat 路径依赖 .NET 运行库、`MathNet.Numerics.dll`、`plat.xml`、`platset.xml` 和 `appset.xml`。没有发现 COM 依赖。`ProConvert.exe` 的 WinForms/ScottPlot 依赖只服务于厂家界面，不参与已确认的运动学和控制器帧格式。

## 7. 抓包与现场事实

现有 `摇摆台.pcapng` 没有 7408/8410 流量。它记录的是 `192.168.15.49` 把 A6T 文本直接发给控制器 `192.168.15.201:9800`，控制器返回 ICMP port unreachable；同时控制器持续 ARP 查询 `192.168.15.101`。这证明：

- `9800` 是 PC 厂家服务端口；
- 控制器不是 A6T 文本服务端；
- 现场 PC 必须拥有 `192.168.15.101` 才能满足当前控制器地址合同。

2026-10-09 的新现场抓包已经补齐正常运行时的 7408/8410 流量。抓包包含 9 条 `0xC0` 位置命令和 11415 条控制器反馈，全部位置命令与权威 `plat.xml` 及 Python 原型逐字节一致。反馈周期中位数为 21.002 ms，序号连续，六轴伺服错误码全程为 0。

正常运动期间 `systemstate=4`、`reccmd=0xC0`、`reccmdret=0` 均保持不变，路径计数始终为 0。这证明正常 CSP 位置运动链路已经可复现，但仍不能把 `reccmdret=0` 或路径计数定义为逐命令完成确认。完整结果见 `M19_A10_field_capture_analysis_20261009.md`。

后续供应商上位机有效抓包进一步确认：

- 回原点使用 `AA 55 00 01 03 FB FB`，存在约 64.4 s 和 9.36 s 两段可重复反馈中断，过渡帧为 `systemstate=3/reccmd=3/reccmdret=1`；
- 三轴摇摆以 50 ms 周期连续发送位置目标，没有独立停止帧；
- 静止断网重连不改变控制器 CSP 状态和位置；
- Roll 32°被逐轴钳位到 200 mm，随后轴1出现 `0x7121 Motor blocked`；
- 伺服故障期间 `systemstate=4/reccmdret=0` 不变，证明二者不能作为动作成功证据；
- Roll 0°目标本身一致，但受故障恢复影响实际用时 5.831 s，供应商程序提前报告完成。

物理急停抓包确认急停没有产生软件停止帧，而是使控制器序号、内部时间和状态全部重启。急停前最后反馈至重新进入CSP约20.071 s，恢复后可以重新发送中心位。当前供应商页面没有取消定位入口，当前 `ECMPlatform` 也没有实现可调用的 `StopPlat`。因此取消定位和软件快速停止属于当前路径不支持的功能，紧急停止依赖物理急停。

现有反馈没有硬限位字段。Roll 32°只证明运动学把目标逐轴钳位到200 mm并触发轴1堵转，不能证明物理限位开关存在或动作。正式软件应拒绝整条不可达姿态，不能沿用逐轴钳位模型。

## 8. 后续真机验收顺序

1. 向厂家取得控制柜电气图或接线证据，确认是否存在未接入反馈协议的物理限位开关。
2. 向厂家取得 `systemstate`、`reccmdret` 和伺服错误码合同；当前路径未实现的取消定位和软件快速停止直接标记为不支持。
3. 对 MS-6222 完成正式坐标标定，并拆分短时噪声、回中重复性和长期航向漂移指标。
4. 设计唯一的直接控制 owner：不可达姿态整条拒绝、六轴反馈闭环完成、错误码失败、回原点长状态、急停重启代际和断网恢复检查。
5. 低幅真机验收通过后删除厂家服务路径，不能长期保留两套可同时发指令的 owner。
